# SLIDERS ablation pilot: direct extraction versus the SLIDERS-style pipeline on two diseases

*Design written 2026-10-28, before any model run of this study. Decision D-42 (Jimmy Lin, 2026-10-28, four answers through the question tool; `DECISIONS.md`). Exploratory: nothing in the frozen pre-registration (v1.0, 2026-10-20) changes, no pinned file is edited, and no registered metric or threshold is touched. The study is reported in `reports/sliders_ablation_findings.md`, generated by `analysis/sliders_ablation/report.py`.*

## 1. Question

The six-disease study extracts genotype–phenotype records with a home-built version of the SLIDERS method (`DECISIONS.md` D-20; `CONTEXT.md` §5): per-paper evidence tables with a verbatim quote on every value, a pinned schema, a rules file, a second-read gatekeeper and deterministic cross-paper reconciliation. Its results so far (every quote found verbatim; 0.36% of model claims judged unsupported by the gatekeeper; `reports/six_disease_run_findings.md`) are attributed to "SLIDERS, powered by Claude". This pilot asks how much of that comes from the SLIDERS-style scaffold rather than from the model: **what does the same model produce on the same papers when asked directly for the final records, with no SLIDERS-style scaffold?**

## 2. Arms

| | Arm S: SLIDERS-style (existing) | Arm D: direct extraction (new) |
|---|---|---|
| Runs | `pv1-ha20`, `pv1-ssadh` (frozen pipeline `pipeline-v1.0`, run 2026-10-20). Not re-run. | `direct-ha20`, `direct-ssadh` |
| Model and route | Claude Opus, one Claude Code helper agent per paper (D-20, D-17) | the same: Claude Opus, one Claude Code helper agent per paper, launched the same way, with the same tools |
| What the helper reads | the paper's Markdown, `extract_v6*.md` (171 lines), `schema_<d>_v5.json`, `extraction_rules_v1.md` | the paper's Markdown and `direct_v1_<d>.md` only |
| Output | five relational tables; every value a `{value, span}` cell with a verbatim quote; `evidence_basis` per status | one JSON document per paper: a publication block and one nested record per individual, with plain values and **no quotes** |
| Downstream | span check, gatekeeper v4 filter, reconciliation (merge policy v4), normalization, phenopackets | conversion to the five-table shape (`span = null`) so the same scripts can read it; reconciliation and normalization run on it; no span check, no gatekeeper filter |

**What arm D removes, item by item.** The evidence-table structure and per-value provenance (SLIDERS' core); the nine SLIDERS extraction rules as a file; the pilot-tuned rules of `extract_v6.md` (label rules, group statements, table symbols, zero counts, stacked cells, the person link for variant fields, the de novo and inheritance rules, normal findings, contradictions, the finish checks); the gatekeeper; the deterministic reconciliation as a step the design depends on (it is still run on D's converted output, for the count, because the baseline carries the one field it needs).

**What arm D keeps, and why.** The task (the same disease, gene, scope sentence and fields, so the outputs are comparable), the project's data standards from `INSTRUCTIONS.md` §2 (use only the paper; "not reported" when the paper does not say; three-state phenotypes; strings as printed), and the 20-item disease checklist (a project device, not a SLIDERS one, and the only way to measure "not reported"). The instruction is written as a careful plain request, about 60 lines, and contains nothing learned in the pilot. Both arms' helpers are agentic (they can read the file in pieces and run a shell), so this pilot ablates the scaffold, not agency.

**Why arm S is not re-run.** The pv1 runs are the records of record, on the same papers, with the same model ID requested; re-running them would cost about $155 and measure run-to-run noise that the 10% repeat already measured (`reports/six_disease_run_findings.md` §6). The eight days between the runs are stated as a limitation; the model ID served to the D helpers is recorded and compared.

## 3. Diseases and papers

- **A20 haploinsufficiency (HA20, *TNFAIP3*)**: the 85 papers of `pv1-ha20`. The development disease: every rule in `extract_v6.md` was tuned on it (D-18), so this is the case most favorable to arm S.
- **SSADH deficiency (*ALDH5A1*)**: the 40 papers of `pv1-ssadh`. Not a development disease.

The same 125 papers were used for the open-weight comparison (D-10), so the write-up can set Claude with SLIDERS, Claude without SLIDERS and DeepSeek with SLIDERS side by side.

**Inputs re-created, not changed.** This container held none of the git-ignored full text. On 2026-10-28 the 125 papers were re-fetched from Europe PMC, PMC and Unpaywall; every file's sha256 equals the one recorded in the corpus manifests on 2026-10-18 to 2026-10-20 (85 of 85, 40 of 40). The four pinned ontology releases were re-downloaded and match their recorded hashes. Supplementary files are re-fetched and re-appended with the same scripts and settings; the regenerated conversion tables are diffed against the committed ones. The proof that arm D reads the text arm S read is the span check of the pv1 output against the re-created Markdown, which must find every pv1 quote (`analysis/sliders_ablation/input_check.json`).

## 4. Measures

All measures are computed by the same scripts on both arms, after arm D's output is complete and committed. Everything is reported per disease, HA20 separately as always (D-18), with Wilson 95% intervals for proportions and exact intervals for the judged samples. No pass/fail threshold.

### 4.1 Primary comparisons

1. **Support, same instrument on both arms.** A new Claude judge, `judge_locate_v1.md`, is given a paper and a shuffled list of claims from both arms, with the arm hidden and arm S's quotes removed. For each claim it must find the passage that supports the value for that person, quote it verbatim, record whom the passage is about, and give one of: `supported`, `partially_supported`, `unsupported`, `not_found`. This differs from gatekeeper v4, which is handed the extractor's own quote; arm D has none, so the judge must locate evidence for both arms alike. The sample: per paper and per arm, up to 2 claims from each of three field groups (variant fields; phenotype statuses, feature rows and checklist cells together; other person-level fields), drawn by seed from the arm's pool of model-class values (the same class rule as `gatekeeper_prep.py`: not bookkeeping, not "not reported", not a field whose value comes from the schema). About 1,500 claims across 125 papers. One judge helper per paper judges both arms at once, so paper and judge are identical across arms. Reported: the unsupported rate per arm (exact 95% CI), the difference with its 95% CI, and the rate per field group. For arm S the gatekeeper's verdicts on the same sampled claims are reported beside the judge's as a check on the instrument. **This is a model's reading, not the error rate**: the pilot showed the gatekeeper understating human-found error by an order of magnitude (`preregistration/analysis_plan.md` §6.4), and the judge is Claude judging Claude in both arms.
2. **HGVS recall against ClinVar's citations** (pre-registration §7.2.2, tiers 1 and 1+2), **overlap with ClinVar** (not precision) and **classification agreement**, by `pipeline/harness/concordance_o2.py` on both arms against **one fresh snapshot** dated 2026-10-28 (so arm S is re-scored too; its registered figures used the 2026-10-19 snapshot and are not replaced).
3. **Text grounding of variant strings.** The share of asserted target-gene variant descriptions (original string, cDNA, protein, transcript) found verbatim in the paper text after whitespace folding, per arm. Arm S carries a quote for each, so its rate is near 1 by construction; arm D's rate is a direct, automatic measure of literal fidelity without any quote.

### 4.2 Secondary and descriptive

4. **Coverage**: individuals, variant rows, distinct target-gene variant keys, feature rows, and the three-state distribution of checklist cells (observed / excluded / not reported).
5. **Three-state behavior**: the share of `excluded` checklist cells, and the judge's unsupported rate among `excluded` statuses, because collapsing silence into "excluded" is the failure the three-state design guards against.
6. **Agreement between arms** per paper: target-gene variant keys (shared / union), checklist status agreement on cells both arms have for the same label and item, label agreement.
7. **Completeness** against Chen 2020 Table S1 for HA20 (D-30; `pipeline/harness/completeness.py`), both arms.
8. **Reconciliation**: identities after merge policy v4 on both arms (arm D carries a source-reference field, so citation merges are possible).
9. **Cost and time**: helper tokens priced at the six-disease run's rate ($5.996 per weighted million, `BUDGET.md`) and wall-clock per paper from the helper transcripts, against `analysis/openweight/claude_helper_stats.json` for arm S on the same papers. Arm S's cost is given with and without its gatekeeper pass ($0.0044 per judged claim).
10. **Structure**: outputs that parse, rows missing required fields, enum values outside the allowed set.

### 4.3 Human audit sheets (drawn now, rated later)

Equal-size samples, 50 claims per arm per disease (200 in all), drawn by a recorded seed from the same pools as the judge sample but independently of it, written as CSV sheets under `adjudication/sliders_ablation/` with the arm hidden and the key in a separate file. No rating page is built (no publishing, Jimmy, 2026-10-21). Rating waits on the panel with the O1 and O5 audits (G1, G5 in the interim paper).

## 5. What we expect, written before the run

Stated so the result can contradict it: arm D will be cheaper and faster per paper; it will produce at least as many individuals and variant rows; it will mark more checklist cells `excluded`; the judge will find a higher unsupported rate in arm D, concentrated in `excluded` statuses and in variant fields of relatives and cited patients; HGVS recall against ClinVar will be similar, because both arms copy the same printed variants. If the unsupported rates turn out alike, the scaffold's value lies in provenance and auditability rather than in accuracy, and the report will say so.

## 6. Isolation and ordering

- Arm D's helpers read only the paper and the instruction file. No reference data is reachable from the extraction side (`pipeline/extract/guard.py`); the ClinVar snapshot lives outside the repository.
- Order: inputs re-created and checked; the design (this file) and the instruction committed; arm D run and committed; then the judge sample, the human-audit sample and the harness. No prompt change after the first helper launches; a problem found in flight is logged, not fixed in the prompt.
- The instruction's sha256 and the launch commit go into `runs/direct-<d>/launch.json` and `manifest.json`.

## 7. Cost and stop rules

| Part | Basis | Estimate |
|---|---|---|
| Arm D extraction, 125 papers | pv1 extraction cost $1.08–1.19 per paper median; a direct run writes no quotes and makes fewer checks | $90–150 |
| Judge, 125 helpers reading one paper each | one paper plus about 12 claims per helper | $20–50 |
| Inputs, conversion, harness, report | scripts, no model | $0 |
| **Total** | | **$110–200** |

Charged to **Contingency** (Jimmy, 2026-10-28). **Ceiling $300: stop and ask past it.** Cost is estimated from helper tokens (`analysis/cost/helper_tokens.py` method) because the session's cost reading lags and freezes; session readings are recorded where available.

## 8. Limitations known in advance

- One baseline instruction. A different plain prompt could do better or worse; the pilot measures this scaffold against this baseline.
- The judge is the same model family in both arms, and a model; the human sheets are the check.
- Arm S ran eight days earlier. The served model ID is compared.
- HA20 is a development disease; SSADH is the cleaner test.
- Arm D is not passed through the gatekeeper, by design: the comparison is between final records as each method would deliver them.
- Two diseases, 125 papers: a pilot, not a general finding.
